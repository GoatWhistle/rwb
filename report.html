Восемь CSV-файлов лежат в схеме raw как есть: каждая колонка — text, даже даты и суммы. Это осознанно: сырой слой хранит данные в том виде, в каком их отдал источник, а приведение типов — работа модели.

2Проблемы в данных

Выгрузка настоящая, и дефекты в ней настоящие. Каждый из них молча искажает отчёт, если его не заметить. Вот что нашлось при осмотре и как модель с этим обходится.

Два «покупателя» в одной таблице

customer_id уникален, но выдаётся заново на каждый заказ — это учётка одного заказа, а не человек. Человек — customer_unique_id: 96 096 людей против 99 441 учётки. Посчитаешь по первому — повторных покупок «не существует».

Решение: ключ покупателя — customer_unique_id, учётка сохранена в заказе атрибутом-ссылкой на источник.

review_id не уникален

814 дублей: один отзыв висит сразу на нескольких заказах. Объявишь review_id первичным ключом — загрузка упадёт или потеряет строки.

Решение: ключ отзыва — пара (review_id, order_id), она уникальна на всех 99 224 строках.

610 товаров без категории

Если отфильтровать их или потерять на JOIN, из выручки молча пропадёт 170 726 R$ — и сумма по категориям перестанет сходиться с общей.

Решение: категория — nullable, в отчётах такие товары видны отдельной строкой «(без категории)».

2 категории без перевода

В файле переводов 71 категория, в товарах — 73. Собери справочник из переводов — и pc_gamer с portateis_cozinha… исчезнут на соединении.

Решение: справочник собран из товаров, перевод — необязательный атрибут.

775 заказов без позиций

В основном отменённые и «unavailable»: заказ создан, но строк товаров у него нет. Внутренний JOIN с позициями молча выбросит их из счётчика заказов.

Решение: соединения от заказа — только LEFT JOIN; число строк сверяется до и после каждого соединения.

Пустой месяц и «дырявые» даты

В ноябре 2016 нет ни одного заказа — GROUP BY молча съест месяц, а отчёту нужны все 24. Плюс пустые строки в датах: у недоставленных заказов нет даты вручения.

Решение: календарь генерируется generate_series, пустые строки при загрузке становятся NULL через NULLIF(trim(x),'').

3Модель core: что с чем связано

Модель — классическая нормализованная схема вокруг заказа: три справочника (покупатели, продавцы, товары + категории) и четыре таблицы фактов (заказы, позиции, платежи, отзывы). Собирается из raw одним скриптом solution/build_core.sql, в одной транзакции, с нуля — запускать можно сколько угодно раз.

Почему именно так

Покупатель = человек

Аналитикам нужны повторные покупки и когорты — значит, ключ обязан быть стабильным от заказа к заказу. customer_unique_id стабилен, customer_id — нет. География двухслойная: в customers — актуальная, по последнему заказу, а в orders — снимок на момент покупки, иначе исторические продажи по регионам считались бы по новым адресам (39 покупателей заказывали из разных штатов).

Позиция, а не «товар в заказе»

order_item_id — порядковый номер строки, не идентификатор. Ключ позиции — (order_id, item_no). Одна строка = одна единица товара, поэтому количество считается как count(*).

Типы и ограничения — в модели

Даты стали timestamp, деньги — numeric(10,2), связи — внешними ключами. CHECK — это правило-ограничение, которое база проверяет сама при каждой вставке: статус только из списка восьми допустимых, оценка только от 1 до 5, цена не меньше нуля. Строка с мусором не запишется — загрузка упадёт и покажет где, вместо того чтобы молча испортить отчёты.

Пересборка с нуля

Скрипт начинается с DROP SCHEMA core CASCADE и заканчивается сверкой числа строк raw против core по каждой таблице. Перенос без потерь — свойство, которое проверяется при каждом запуске, а не однажды.

4Как что считается

Выручка

Сумма цен товаров (price) в заказах со статусом delivered. Доставка (freight_value) — не выручка площадки: с ней итог был бы 15,42 млн вместо 13,22 млн. Отменённые и потерянные заказы выручкой не становятся. Итог сходится тремя независимыми путями: по месяцам, по категориям и по продавцам.

Средний чек

Сначала сумма price + freight по заказу, потом среднее по заказам. Чек — свойство заказа, покупатель платит и за доставку. Посчитаешь на уровне строки — получишь 139.97, без доставки — 119.98; оба ответа неверны и означают перепутанный уровень агрегации.

5Ответы на вопросы бизнеса

Все запросы ходят только в core — в этом смысл модели: правильная цифра получается коротким запросом, а не археологией по сырым файлам. Все пять контрольных значений сошлись.

В1. Выручка и заказы по месяцам

Площадка выросла от 4 заказов в сентябре 2016 до ~7 000 в месяц к 2018 году. Пик — ноябрь 2017, «чёрная пятница»: 987 765 R$. Ноябрь 2016 — месяц без единого заказа: он есть в отчёте только потому, что календарь сгенерирован, а не собран из данных.

Что мы называем «числом заказов»

В колонке «заказов» — все оформленные за месяц; выручка — только по доставленным. Задание фиксирует выбор статусов лишь для выручки («решите, какие заказы считать выручкой»), определение счётчика заказов остаётся за нами. Вариантов три: все оформленные; только доставленные (октябрь 2016 — 265 вместо 324); оформленные без отменённых и «unavailable» (293). Мы считаем все оформленные: заказ — событие спроса, и оно произошло в месяц оформления, какой бы ни была дальнейшая судьба заказа; два других варианта фильтруют спрос задним числом по исходу доставки и прячут потери. Разрыв между колонками — сам по себе сигнал: в октябре 2016 оформлено 324 заказа, доехали до покупателя 265, 31 отменился, 28 зависли в промежуточных статусах. Контрольные точки задания — 24 строки, нулевой ноябрь, итог 13 221 498.11 — сходятся при любом из трёх определений, поэтому выбор проговорён здесь явно.

SQL — выручка и заказы по месяцам 
-- календарь генерируем: ноябрь 2016 пуст и иначе выпадет из отчёта
WITH months AS (
    SELECT generate_series('2016-09-01'::date, '2018-08-01', interval '1 month')::date AS month
),
monthly AS (
    SELECT date_trunc('month', o.purchased_at)::date AS month,
           count(DISTINCT o.order_id) AS orders_cnt,
           coalesce(sum(i.price) FILTER (WHERE o.status = 'delivered'), 0) AS revenue
    FROM core.orders o
    LEFT JOIN core.order_items i USING (order_id)
    GROUP BY 1
)
SELECT m.month, coalesce(t.orders_cnt, 0), coalesce(t.revenue, 0)
FROM months m LEFT JOIN monthly t USING (month)
ORDER BY m.month;

Разбор по словам

WITH months AS (…)WITH создаёт временную подтаблицу с именем — дальше к ней можно обращаться, как к обычной таблице. AS — «назовём её вот так». Здесь их две: months (календарь) и monthly (факты из данных).
generate_series('2016-09-01'::date, '2018-08-01', interval '1 month')Функция-«генератор»: выдаёт ряд значений от первого до второго аргумента с шагом из третьего. Здесь — 24 даты, по одной на месяц. interval '1 month' — тот самый шаг «один месяц».
::dateПриведение типа: текст '2016-09-01' превращается в настоящую дату. Двойное двоеточие — синтаксис Postgres, читается «как дата».
SELECT … AS monthSELECT — «выбрать и показать вот эти колонки». AS month — дать колонке имя.
FROM core.orders oFROM — из какой таблицы брать строки. Буква o — псевдоним: дальше вместо длинного core.orders пишем o, поэтому o.status — «колонка status таблицы заказов».
LEFT JOIN core.order_items i USING (order_id)JOIN — приклеить к каждому заказу его строки из другой таблицы. USING (order_id) — клеить по равенству колонки order_id в обеих. LEFT — важно: заказы, которым пары не нашлось (775 заказов без позиций), не выбрасывать, а оставить с пустыми значениями. Обычный JOIN их бы молча удалил.
date_trunc('month', o.purchased_at)«Обрезать» дату до начала месяца: 14 мая 2017 18:33 → 1 мая 2017. Так все заказы одного месяца получают одинаковую метку, по которой их можно сгруппировать.
count(DISTINCT o.order_id)count — посчитать строки. DISTINCT — «только разные»: после склейки с позициями заказ из трёх товаров превратился в три строки, без DISTINCT он посчитался бы трижды.
sum(i.price) FILTER (WHERE o.status = 'delivered')sum — сложить значения. FILTER (WHERE …) — в сумму пропускать только строки, прошедшие условие: здесь — только доставленные заказы. Отменённые в выручку не попадают.
coalesce(x, 0)«Если x пустой (NULL) — взять 0». У ноября 2016 нет ни заказов, ни выручки; без coalesce в отчёте стояла бы пустота вместо нуля.
GROUP BY 1Сгруппировать строки по первой колонке из SELECT (месяцу) и посчитать count/sum внутри каждой группы. «1» — просто ссылка на позицию колонки, чтобы не повторять выражение.
FROM months m LEFT JOIN monthly tФинал: к полному календарю (24 месяца) прикладываем посчитанные факты. LEFT JOIN снова принципиален — у ноября 2016 фактов нет, но строка месяца обязана остаться.
ORDER BY m.monthОтсортировать результат по месяцу, от раннего к позднему.
✓ Контроль: 24 строки, одна нулевая, итого 13 221 498.11

SQL — топ продавцов 
SELECT s.seller_id, s.city, s.state,
       count(DISTINCT i.order_id) AS orders_cnt,
       count(*) AS units,
       sum(i.price) AS revenue
FROM core.order_items i
JOIN core.orders  o USING (order_id)

WHERE o.status = 'delivered'

Разбор по словам

FROM core.order_items iИдём от позиций, а не от заказов — выручка продавца складывается из его строк. В заказе могут быть товары разных продавцов, и сумма целого заказа продавцу не принадлежит.
JOIN core.orders o USING (order_id)Приклеиваем заказ к каждой позиции — он нужен ради статуса. Обычный (внутренний) JOIN здесь безопасен: позиций без заказа в данных нет, мы это проверили.
JOIN core.sellers s USING (seller_id)Приклеиваем продавца — из его таблицы берём город и штат.
WHERE o.status = 'delivered'WHERE — фильтр строк до всякого подсчёта: дальше идут только позиции доставленных заказов.
count(DISTINCT i.order_id)В скольких разных заказах были товары продавца. Без DISTINCT заказ с двумя его товарами посчитался бы дважды.
count(*)Число строк в группе. Одна строка позиции = одна единица товара, поэтому это и есть «сколько единиц продал».
sum(i.price) AS revenueСумма цен только его позиций — выручка продавца. AS revenue — имя колонки, на него же ссылается сортировка ниже.
GROUP BY s.seller_id, s.city, s.stateОдна группа = один продавец: все его позиции сворачиваются в одну строку результата. Город и штат перечислены, потому что всё, что стоит в SELECT вне агрегатных функций, обязано быть в GROUP BY.
ORDER BY revenue DESCСортировка по выручке. DESC (descending) — по убыванию: самый крупный сверху.
LIMIT 10Показать только первые 10 строк результата — топ-10.

SQL — средний чек 
-- чек — свойство заказа: сначала сумма по заказу, потом среднее
WITH per_order AS (
    SELECT i.order_id,
           sum(i.price + i.freight_value) AS order_total,
           count(*) AS lines
    FROM core.order_items i
    JOIN core.orders o USING (order_id)
    WHERE o.status = 'delivered'
    GROUP BY i.order_id
)
SELECT round(avg(order_total), 2) AS avg_check,
       round(avg(lines), 2)       AS avg_lines
FROM per_order;

Разбор по словам

WITH per_order AS (…)Весь смысл запроса — в двухступенчатости. Первая ступень (эта подтаблица) сворачивает строки до заказов, вторая — усредняет заказы. Пропустишь первую ступень — получишь среднюю строку (139.97), а не средний чек.
sum(i.price + i.freight_value)Внутри одного заказа складываем по каждой строке цену товара и стоимость его доставки: покупатель платит за всё вместе. Это и есть чек заказа.
count(*) AS linesСколько строк в заказе — контрольное число: если «средний чек» вдруг равен средней строке, уровень перепутан.
WHERE o.status = 'delivered'Чек считаем только по доставленным заказам — тем же, что входят в выручку.
GROUP BY i.order_idОдна группа = один заказ: подтаблица per_order содержит одну строку на заказ с его полной суммой.
avg(order_total)avg — среднее арифметическое. Усредняем уже готовые чеки заказов — каждый заказ весит одинаково, сколько бы строк в нём ни было.
round(…, 2)Округлить до двух знаков после запятой — это деньги.
✓ Контроль: 159.88 (ловушки 119.98 и 139.97 обойдены)

В4. Покупатели и повторные покупки

96 096 человек, из них 2 997 вернулись хотя бы за второй покупкой — 3,12%. Цифра честная только на ключе customer_unique_id: по учёткам получилось бы 99 441 «покупателей» и ровно ноль повторных.

SQL — покупатели и возвраты 
WITH per_customer AS (
    SELECT customer_unique_id, count(*) AS orders_cnt
    FROM core.orders
    GROUP BY 1
)
SELECT count(*) AS customers_total,
       count(*) FILTER (WHERE orders_cnt >= 2) AS returned,
       round(100.0 * count(*) FILTER (WHERE orders_cnt >= 2) / count(*), 2) AS pct
FROM per_customer;

Разбор по словам

WITH per_customer AS (…)Первая ступень: по одной строке на человека с числом его заказов.
SELECT customer_unique_id, count(*)Группируем заказы по customer_unique_id — стабильному идентификатору человека — и считаем, сколько заказов у каждого. Возьми тут customer_id — у каждого «покупателя» оказался бы ровно один заказ, и повторных не нашлось бы вовсе.
GROUP BY 1Группировка по первой колонке SELECT — идентификатору человека.
count(*)Во внешнем запросе считает строки per_customer — то есть людей. Всего их 96 096.
count(*) FILTER (WHERE orders_cnt >= 2)Тот же счётчик, но через фильтр проходят только люди с двумя и более заказами — вернувшиеся.
100.0 * … / count(*)Доля в процентах. 100.0 — именно с точкой: поделив целое на целое, SQL отбросил бы дробную часть и выдал 0. Дробное число в формуле переводит весь расчёт в дробные.
round(…, 2)Округление до сотых процента: 3.12.
✓ Контроль: 96 096 покупателей, 3,12% вернулись

В5. Выручка по категориям

74 категории. Крупнейшая — «красота и здоровье», 9,3% выручки. Товары без категории не выброшены — это 1,3% выручки, и без них сумма по категориям не сошлась бы с общей.

SQL — выручка по категориям 
SELECT coalesce(p.category_name, '(без категории)') AS category,
       sum(i.price) AS revenue,
       round(100 * sum(i.price) / sum(sum(i.price)) OVER (), 2) AS pct
FROM core.order_items i
JOIN core.orders   o USING (order_id)
JOIN core.products p USING (product_id)
WHERE o.status = 'delivered'
GROUP BY 1
ORDER BY revenue DESC;

Разбор по словам

coalesce(p.category_name, '(без категории)')«Если категория пустая (NULL) — подставить подпись». Так 610 товаров без категории не исчезают из отчёта, а образуют собственную строку. Выбросишь их — сумма по категориям разойдётся с общей выручкой на 170 тысяч.
JOIN core.products p USING (product_id)Приклеиваем карточку товара ради его категории. Внутренний JOIN безопасен: позиций без товара нет, проверено при осмотре данных.
WHERE o.status = 'delivered'В расчёт идут только доставленные заказы — то же определение выручки, что и везде.
sum(i.price) AS revenueВыручка категории — сумма цен её товаров.
sum(sum(i.price)) OVER ()Самое хитрое место. Внутренний sum(i.price) — выручка категории (после группировки). Внешний sum(…) OVER () — оконная функция: она проходит по уже сгруппированным строкам и складывает их все. OVER () с пустыми скобками значит «окно = весь результат». Итог: в каждой строке рядом с выручкой категории доступна общая выручка — и можно поделить одно на другое.
100 * … / …Доля категории в процентах от общей выручки.
GROUP BY 1Группировка по первой колонке — названию категории (уже с подставленной подписью для пустых).
ORDER BY revenue DESCКрупнейшие категории сверху.
