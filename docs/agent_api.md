# Backend метрик и AI-чата

Базовый адрес локального сервиса: `http://127.0.0.1:8090`.
Диалоги и события инструментов: `.local/agent.sqlite3` (SQLite).
PostgreSQL содержит данные маркетплейса и отдельную схему `ai` для эмбеддингов.
Код локального Codex gateway и ключи исключены из Git.

## Метрики

`GET /api/metrics` возвращает `metrics_version` и `reports`: ID, название,
SQL, зерно, единицы, определения, ограничения, допустимые фильтры.
Текущие группы: `dashboard.kpi`, `dashboard.checks`, `dashboard.monthly`,
`dashboard.states`, `dashboard.lateness`, `dashboard.sellers`, `block_a.1`–`block_a.5`.
Поля KPI можно запрашивать отдельно: например `dashboard.kpi.otd`.
`otd` — доля 0–1, `returned_pct` блока А — проценты 0–100.

`POST /api/metrics/query`:

```json
{
  "metric_id": "dashboard.monthly",
  "filters": {"start_date": "2017-01-01", "end_date": "2018-09-01", "states": ["SP"]}
}
```

`end_date` исключается. Дополнительные фильтры: `seller_ids`, `categories`
(коды категорий на португальском; `(без категории)` для NULL).
Выручка при фильтрах по позициям относится к выбранным позициям;
средний чек и показатели исполнения — к целым заказам с такими позициями.
Существующие ограничения периода дашборда сохраняются, даже если запросить
более широкий интервал. Блок А вне первого отчёта по умолчанию использует весь снимок.

Ответ содержит `table`, `definition`, `units`, `limitations`, `filters`, `sql`,
`parameters`, `metrics_version`, `data_version`. Денежные SQL numeric передаются
строками без потери точности. Колонки содержат имя и PostgreSQL OID либо JSON-тип.
При необходимости переводите decimal-строки в числа только для отрисовки графика.
`truncated` сообщает об усечении. Не складывайте уникальные заказы по категориям
или продавцам и не усредняйте готовые средние разных групп.

Новый отчёт, в том числе блок Б, добавляется JSON-записью в `backend/catalog/`.
Исполняется статический параметризованный SELECT; HTTP-клиент не передаёт свой SQL
в API метрик. Поддерживаются те же фильтры через общий слой orders/items.
После добавления записи перезапустите backend. Фронтенд использует ID из каталога.

## Чат

`POST /api/chat/stream`, ответ `text/event-stream`. Используйте `fetch` с POST
и чтением response body; нативный браузерный EventSource отправляет GET.

```json
{
  "session_id": "demo-1",
  "message": "Почему здесь такая доля доставок вовремя?",
  "dashboard_context": {
    "widget_id": "delivery-on-time",
    "metric_id": "dashboard.kpi.otd",
    "displayed_value": 0.9323,
    "filters": {},
    "data_version": "версия из ответа API метрик",
    "metrics_version": "версия из ответа API метрик"
  }
}
```

`session_id` необязателен на первом запросе: сервер вернёт его в событиях.
Используйте полученный ID для продолжения диалога. Передавайте актуальный контекст
при каждом сообщении. Диалоги переживают перезапуск backend благодаря SQLite.
Одновременно выполняется один запрос на диалог; повторный получает HTTP 409.

Фрейм SSE:

```text
event: text_delta
data: {"run_id":"...","session_id":"demo-1","delta":"Доля рассчитана..."}

```

События:

| event | Дополнительные поля |
|---|---|
| `run_started` | `metrics_version` |
| `tool_started` | `call_id`, `name`, `arguments` |
| `tool_finished` | `call_id`, `name`, `ok`, `result` или `error`, время выполнения |
| `text_delta` | `delta` — добавляемый текст |
| `table` | `table_id`, `columns`, `rows`, `truncated` |
| `chart` | `type`: `line`/`bar`, `title`, `table_id`, `x`, `y`: массив колонок |
| `sources` | `items`: SQL с параметрами и определениями, ID заказов/отзывов |
| `done` | `text` — окончательный авторитетный текст ответа |
| `error` | `code`, `message`; терминальное событие |

Все события содержат `run_id` и `session_id`. Комментарии `: heartbeat` можно
игнорировать. Связывайте графики с таблицами по `table_id`. Источники отзывов
адресуются парой `review_id` + `order_id`, поскольку один review_id не уникален.
При `done` замените накопленный текст окончательным. Закрытие fetch через
AbortController отменяет выполнение агента и обращение к gateway.

SSE начинается HTTP 200, поэтому последующие ошибки передаются событием `error`.
Валидация запроса до начала потока возвращает HTTP 422.
Секреты и строки подключения не включаются в события ошибок.

## Проверяемые сценарии

- «Покажи выручку по месяцам» → готовый отчёт, таблица и line-график.
- «Почему здесь такая цифра?» с контекстом → точное определение виджета и его SQL.
- «Что происходило с заказом `<полный ID>`?» → даты, позиции, продавцы, платежи, отзывы.
- «Найди жалобы на недокомплект» → русский запрос, португальские оригиналы и ID.
- «Где проблемы с доставкой и что пишут покупатели?» → SQL по всей выборке плюс примеры отзывов.
- «Почему платежи отличаются от выручки?» → отдельные суммы товара, доставки и платежей, статусы.

Формулы текущего дашборда сохранены: последний отзыв определяется сначала по
created_at. У сценария в review.md другое правило (сначала answered_at).
Агент должен обозначать выбранное определение. Отрицательная длительность этапа
исключается из его медианы; доставка вовремя сравнивается по календарной дате.
Отзывы — примеры, а не подсчёт частоты всех жалоб и не доказательство виновности.
