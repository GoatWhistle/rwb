# Ревью решения и рекомендации по развитию

Дата проверки: 28 октября 2026 года.

Проверены [условия кейса](handout.md), [вопросы блока А](tasks.md),
[конспект критериев оценки](marketplace_case.md),
[сборка модели](../solution/build_core.sql) и
[аналитические запросы](../solution/answers_block_a.sql).

Блок А проходит контрольные значения. Для текущего сценария рекомендуется
оставить PostgreSQL основой, добавить быстрые витрины и единый интерфейс
с ИИ-помощником для оператора и аналитика. ClickHouse можно рассматривать
как следующий этап масштабирования: на данном датасете он не требуется
для достижения хорошей скорости.

## 1. Проверка реализации

Модель дважды собрана на исходном датасете Olist в отдельном временном
PostgreSQL 16. Выполнены все пять запросов. Число строк фактов совпало
с `raw`, обе сборки завершились успешно.

| Проверка | Фактический результат |
|---|---|
| А1: выручка по месяцам | 24 строки; ноябрь 2016 — нулевой; сумма **13 221 498,11** |
| А2: лучший продавец | **226 987,93** |
| А3: средний чек | **159,88**; строк и единиц на заказ — **1,14** |
| А4: повторные покупки | **96 096** покупателей; **2 997** повторных; **3,12%** |
| А5: категории | **74**; крупнейшая — **1 233 131,72**; общая сумма **13 221 498,11** |

### Первая задача

В первом запросе корректно реализованы календарь, сохранение пустого месяца
и защита количества заказов от размножения после соединения с позициями.
За отчётный период получено 99 421 заказ.

Нужно явно зафиксировать выбранную трактовку показателей:

- месяц определяется датой оформления `purchased_at`;
- количество заказов включает все статусы;
- выручка — сумма `order_items.price` только для заказов `delivered`;
- доставка в выручку не входит, но входит в средний чек покупателя.

Зерно позиций и платежей, составные ключи, идентификация покупателя через
`customer_unique_id` и сохранение товаров без категории в текущем решении
работают правильно.

### Что стоит поправить перед дашбордом и новыми заданиями

**1. Теряется география на момент заказа.**

В `solution/build_core.sql`, начиная со строки 75, справочник покупателей
сохраняет адрес последнего заказа. При использовании этого адреса для
исторических продаж **43 заказа получают другой штат, 130 — другой город**.
Всего у 272 заказов отличается хотя бы один атрибут адреса: индекс, город
или штат.

Для анализа по региону заказа нужно сохранить соответствующий снимок
адреса в `core.orders` или отдельной таблице по `customer_id`. Текущую
географию покупателя можно оставить отдельным атрибутом справочника.
Блок А от этого ограничения не страдает.

**2. Сверки не останавливают некорректную сборку.**

В `solution/build_core.sql`, начиная со строки 213, проверки только печатают
количества после `COMMIT`. В изолированной тестовой базе был добавлен заказ
без соответствующего покупателя. Сборка завершилась с кодом 0, но заказ
исчез из `core` из-за `INNER JOIN`: в `raw.orders` осталось 99 442 строки,
в `core.orders` — 99 441.

Нужны проверки с `RAISE EXCEPTION` до фиксации транзакции: сохранение
ожидаемого количества фактов, отсутствие потерянных связей, сверка сумм
и контрольных ответов. Для покупателей ожидаемое количество следует
сравнивать с числом уникальных `customer_unique_id`, учитывая намеренную
дедупликацию.

**3. Пересборка удаляет зависимые витрины.**

`DROP SCHEMA core CASCADE` в строке 10 удалил созданное для проверки
материализованное представление в `mart`. Для полного пересоздания модели
это допустимо, но общий запуск должен затем восстанавливать витрины.

## 2. ClickHouse: соответствие условиям и целесообразность

Дополнительный аналитический слой ClickHouse не противоречит явным
ограничениям кейса. Условия требуют сохранять `raw`, строить `core`
и считать ответы из модели. Полную замену выданного PostgreSQL-окружения
они явно не оговаривают, поэтому подтвердить допустимость такой замены
по репозиторию нельзя.

Рекомендуется сохранить обязательное решение и контрольные ответы
в PostgreSQL, а ClickHouse при необходимости наполнять из `core`.

Практическая схема:

```text
PostgreSQL raw → PostgreSQL core → витрины PostgreSQL / ClickHouse → интерфейс и ИИ
```

Если добавлять ClickHouse:

- Сделать отдельные витрины **на уровне заказа** и **на уровне позиции**.
  Платежи и отзывы агрегировать отдельно перед соединением, чтобы избежать
  размножения строк и сумм.
- Загрузить снимок в локальные таблицы `MergeTree`; денежные значения
  сохранить как `Decimal`.
- Для статичного датасета использовать пакетную загрузку и воспроизводимое
  обновление снимка. CDC на этом этапе не требуется.
- Сверять количество строк, суммы и точные количества уникальных заказов
  между системами.

Для загрузки подходит `INSERT … SELECT` через функцию `postgresql(...)`.
Само чтение через эту функцию обращается к PostgreSQL, поэтому для
самостоятельного обслуживания запросов данные нужно сохранить в ClickHouse.
См. [документацию функции postgresql](https://clickhouse.com/docs/reference/functions/table-functions/postgresql)
и [движка MergeTree](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/mergetree).

### Измеренная скорость PostgreSQL

| Вариант первого отчёта | Медиана серверного времени |
|---|---:|
| Текущий запрос по `core` | **86,831 мс** |
| Чтение готовой месячной витрины PostgreSQL | **0,027 мс** |

Измерения выполнены после `ANALYZE`: по пять прогретых запусков через
`EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)` в локальном временном
контейнере PostgreSQL 16 с хранилищем `tmpfs`. Указано серверное время
выполнения без сетевой задержки и времени отображения интерфейса.
Это локальная проверка, а не оценка производственной нагрузки.
Сравнение с ClickHouse не проводилось.

Медианы времени остальных запросов блока А составили примерно 12–118 мс.
Материализованные представления сохраняют рассчитанный результат и хорошо
подходят для такого статичного набора. См.
[документацию PostgreSQL](https://www.postgresql.org/docs/16/rules-materializedviews.html).

Переход на ClickHouse стоит обосновывать измерениями при росте объёма,
сложности запросов и числа одновременных пользователей. На текущем наборе
данных витрины и кеширование уже обеспечивают быстрый интерфейс.

## 3. Дашборд: стек и концепция

Для дашборда с ИИ-помощником рекомендуется **Streamlit + Plotly + PostgreSQL**.
Streamlit позволяет собрать фильтры, таблицы, графики и чат в одном
приложении. Результаты SQL можно кешировать с учётом версии датасета.
См. [документацию кеширования Streamlit](https://docs.streamlit.io/develop/concepts/architecture/caching).

Если нужен преимущественно классический BI с самостоятельной сборкой
графиков аналитиками, подойдёт **Superset**: у него есть SQL-редактор
и слой определения метрик. См.
[документацию Superset](https://superset.apache.org/docs/).

Предлагаются два режима интерфейса:

- **Оператор:** поиск заказа, хронология статусов и дат, товары и продавцы,
  платежи, отзывы, обнаруженные несоответствия. Интерфейс помогает быстро
  собрать сведения по обращению и выбрать следующий шаг разбора.
- **Аналитик:** динамика продаж, категории и продавцы, доставка, фильтры
  и возможность задать вопрос к выбранному срезу. Интерфейс помогает
  выявлять изменения и выбирать сегменты для дальнейшего анализа.

### Основные показатели

| Показатель | Формула и источник | Уровень расчёта |
|---|---|---|
| Выручка по правилам кейса | `sum(core.order_items.price)` для `core.orders.status = 'delivered'` | Позиция |
| Заказы | `count(distinct core.orders.order_id)`; явно указать учитываемые статусы | Заказ |
| Средний чек | Среднее от суммы `price + freight_value` внутри доставленного заказа | Заказ |
| Доля просрочек | Доставленные позже обещанной даты / доставленные с обеими известными датами; источник — `core.orders` | Заказ |

Для просрочки сравнивать `delivered_at::date > estimated_delivery_date`,
поскольку обещанный срок хранится как дата. Пропуски дат показывать отдельно:
в данных есть **8 доставленных заказов без даты вручения**.

Основные срезы: период оформления, продавец, категория и регион покупателя
на момент заказа. Исторический регион следует использовать после доработки
модели, описанной выше. При фильтрах по продавцу или категории нужно явно
определить, показывается ли чек целого заказа, содержащего выбранные товары,
или только сумма выбранных позиций.

Средние и доли пересчитываются из исходных числителей и знаменателей.
Уникальные заказы нельзя складывать по продавцам или категориям: один
заказ может встречаться в нескольких группах. Выручка по позициям аддитивна
при разбиении на непересекающиеся группы.

По условиям **реализация дашборда необязательна**. Оценивается его концепция:
пользователи, решения, формулы, источники, срезы и ограничения.
См. [раздел «Что сдавать»](handout.md).

## 4. ИИ-помощник для оператора и аналитика

Основной сценарий — быстро ориентироваться в датасете через ИИ:
находить заказы, получать срезы, искать отзывы и разбираться в показателях.
Для этого предлагается помощник с SQL-инструментами и поиском по текстам.

| Пользователь и боль | Пример запроса | Что делает помощник |
|---|---|---|
| Оператор долго собирает сведения из разных таблиц | «Что происходило с заказом `<ID>`?» | Собирает карточку заказа, платежи, сроки и отзывы; показывает подтверждённые факты |
| Аналитик тратит время на SQL и выяснение определений | «Покажи выручку и средний чек по месяцам» | Находит определения метрик, выполняет SQL, возвращает таблицу, график и использованные фильтры |
| Оператору или аналитику трудно найти похожие обращения | «Найди жалобы на недокомплект в этой категории» | Ищет по смыслу в отзывах, применяет фильтры и показывает тексты с идентификаторами заказов |
| Аналитик разбирается в расхождениях отчётов | «Почему сумма платежей отличается от выручки?» | Сопоставляет определения, статусы и суммы, показывает составляющие расхождения |

Распределение работы:

- **SQL** получает карточки заказов и считает показатели по всей нужной
  выборке.
- **RAG** находит определения метрик, описание схемы и релевантные отзывы.
- **Агент** выбирает инструменты, уточняет неоднозначные формулировки
  и собирает ответ с SQL, фильтрами и источниками.

Для первого варианта достаточно **одного агента** с инструментами
`get_order`, `query_metrics`, `search_reviews`, `run_quality_checks`.
Отзывы можно индексировать в PostgreSQL через `pgvector`, который
поддерживает векторный поиск. См.
[документацию pgvector](https://github.com/pgvector/pgvector).

Словарь метрик должен закреплять определения из кейса: статусы для выручки,
включение доставки в чек, использование `customer_unique_id`, правила
обработки пустых категорий и уровень расчёта каждой метрики. Это позволит
помощнику давать согласованные ответы на разные формулировки вопросов.

### Предметный сценарий демонстрации

Запрос: **«Где проблемы с доставкой и что об этом пишут покупатели?»**

На исходном датасете получены следующие значения:

| Доставленные заказы с известными датами | Заказов | Заказов с отзывом | Средняя последняя оценка |
|---|---:|---:|---:|
| Доставлены вовремя | 89 936 | 89 443 | **4,29** |
| Доставлены позже обещанной даты | 6 534 | 6 381 | **2,27** |

Для каждого заказа выбран один последний отзыв: по `answered_at DESC
NULLS LAST`, затем `created_at DESC`, затем `review_id` для однозначного
выбора. Заказы без отзыва не входят в среднее оценки.

Помощник может показать проблемные сегменты, объём проблемы и подтверждающие
отзывы. Это наблюдаемая связь; конкретную причину задержки и ответственность
отдельного продавца данные устанавливают не всегда. Демонстрация работает
с историческим снимком, а не с текущими операционными заказами.

### Как обосновать дополнительные баллы

Нужна проверяемость: набор контрольных вопросов, корректные суммы, ссылки
на найденные отзывы, журнал использования ИИ и объяснение решений,
принятых командой.

По [конспекту критериев](marketplace_case.md), 15 баллов относятся
к прозрачному и проверенному использованию ИИ. Наличие RAG или нескольких
агентов само по себе баллы не гарантирует.

## 5. Приоритет работ

1. Доработать историческую географию, проверки и порядок пересборки витрин.
2. Зафиксировать определения метрик и подготовить витрины PostgreSQL.
3. Описать концепцию дашборда; при наличии времени реализовать интерфейс
   оператора и аналитика.
4. Добавить SQL/RAG-помощника с проверяемыми ответами и источниками.
5. Представить ClickHouse как обоснованный этап развития; внедрять его
   при подтверждённой потребности в дополнительной производительности.
